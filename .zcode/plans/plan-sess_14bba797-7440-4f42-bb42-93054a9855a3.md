# 授权弹窗与启动加载问题修复方案

## 修复目标
1. 关闭授权开关后不再误弹窗（问题 A）
2. 开启开关时仅在确实需要授权时弹窗，且输码失败有明确反馈（问题 B）
3. 进应用能稳定获取用户信息（问题 C）
4. 本地 server submodule 与线上部署版本对齐（问题 D）

## 改动文件清单（共 5 处）

### 1. `src/stores/auth.ts` —— 区分网络错误 vs 未授权（核心修复）

**问题**：`checkAuth` 的 catch（:59-67）把任何异常（网络超时、5xx、DB 错误）都置 `isAuthorized = false`，导致弹窗误触发。

**改动**：
- State 新增两个字段（不持久化）：
  - `authRequired: boolean`（服务端是否要求授权，对应线上授权开关）
  - `networkError: boolean`（本次检查是否为网络错误，区别于"确实未授权"）
- `checkAuth` 逻辑重写：
  - 成功响应：读 `response.data.authRequired`（旧服务端无该字段时默认 true）和 `authorized`，分别写入两个字段；只有 `authorized=true` 才 `isAuthorized=true`
  - catch 分支：**不再**把 `isAuthorized` 强制设 false（保留持久化的上次成功状态），改为 `networkError = true`，避免把瞬态错误变成"未授权"
  - 删除 `errorMessage` 在 catch 里覆盖网络文案的逻辑，改为只在确实未授权时设置
- `verifyCode` 同理：catch 时不改 `isAuthorized`，只设 `networkError`
- persist 的 `pick` 不变（仍只持久化 `isAuthorized/authCode/deviceId`），新增字段是会话级

### 2. `src/components/Modal/GlobalAuthModal.vue` —— 三态弹窗

**问题**：`showModal = computed(() => !isAuthorized)`（:66）把网络错误和未授权混为一谈。

**改动**（参考 GlobalUpdateModal 的 ref+watch 模式）：
- `showModal` 改为同时判断：`!isAuthorized && authStore.authRequired && !authStore.networkError`
  - 开关关闭（authRequired=false）：永不弹窗
  - 网络错误（networkError=true）：不弹授权码输入框，弹"网络异常，重试"对话框
  - 确实未授权：弹授权码输入框（现有 UI）
- 新增"网络错误"视图分支：图标改为 Network/Wifi-off，按钮改为"重试"（调用 `authStore.checkAuth()`），文案"无法连接服务器，请检查网络后重试"
- 主视图（授权码输入）保留现有样式，只在 `authRequired && !networkError && !isAuthorized` 时显示

### 3. `src/utils/init.ts` 或 `src/App.vue` —— 修复启动 cookie 时序竞态（问题 C）

**确认事实**：`User.vue:196` 在 `onBeforeMount` 调用 `checkLoginStatus → getLoginState`，与 `App.vue:124` 的 `await syncNativeCookies()` 并发，存在时序竞态。`updateUserData` 仅在登录流程中调用，但 `getLoginState`（验证登录态）依赖 cookie 已注入原生层。

**改动**（`src/App.vue`）：
- 在 `App.vue:124` 的 `syncNativeCookies()` 调用处增加 **2 次重试 + 短退避**（200ms），失败不阻断启动（保持现有 try/catch）
- 把"cookie 同步完成"作为一个轻量级 promise 暴露出来（模块级 `let cookiesReadyResolvers` 数组 + `whenCookiesReady()` 导出），让依赖 cookie 的组件可 await

**改动**（`src/components/Layout/User.vue`）：
- `checkLoginStatus` 开头 `await whenCookiesReady()`（仅在 Capacitor 环境），确保原生 cookie 同步完成后再校验登录态
- `getLoginState` 失败时若本地有缓存登录态，保持现有"继续使用本地数据"分支（:174-177），不再因一次失败清空状态

### 4. `src/utils/request.ts` —— axios-retry 覆盖 cookie 失效（可选但推荐，配合问题 C）

**问题**：axios-retry 默认只在网络错误/5xx 重试，登录态校验返回 4xx（cookie 临时未就绪被服务端判未登录）不重试。

**改动**：
- `axiosRetry` 配置增加 `retryCondition: (error) => axiosRetry.isNetworkOrIdempotentRequestError(error) || error.response?.status === 401`
  - 注意：仅对 GET（如 `/login/status`、`/user/account`）生效，POST 不受影响（axios-retry 默认只重试幂等请求）
- 增加 `retryDelay: axiosRetry.exponentialDelay`（显式化，虽是默认值）

### 5. `server/` submodule —— 同步到新版（问题 D）

**改动**（命令，需在 plan 批准后执行）：
- `git submodule update --remote server`（把 server/ 从 8856f8c 更新到 91ec0ab）
- 提交 `.gitmodules` 无变化 + submodule 指针更新
- **不改 server/ 内代码**（遵循 AGENTS.md：server 改动去 xiaoxiongmusic-server 仓库）

## 不做的事（明确边界）
- 不重写 CapacitorHttp 适配器（现有手动 cookie 注入逻辑保留）
- 不动后端代码（线上已是新版，本地 submodule 同步即可）
- 不引入 p-retry 等新依赖（axios-retry + 少量手写重试足够）
- 不改 `deviceId` 生成逻辑、不清理持久化的 `isAuthorized`（持久化的成功状态反而是网络抖动时的兜底）

## 验证方式
1. **问题 A**：服务端把 capacitor 端开关关闭 → 冷启动 → 不应弹窗；即便断网启动也不弹授权码框，只弹网络重试
2. **问题 B**：开关开启 + 未授权设备 → 弹授权码框；输错码有红色提示；断网时弹网络重试而非授权框
3. **问题 C**：已登录用户冷启动 → Nav 用户头像/昵称正常显示，不再出现"获取用户信息失败"
4. **问题 D**：`git diff --submodule` 显示 server 从 8856f8c → 91ec0ab
5. 全程在 Android Studio Logcat 用 TAG 过滤验证：`AUTH_LOG`、`[AuthCheck]`、`🍪`、`🔐 [User]`
